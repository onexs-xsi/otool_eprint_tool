# 标签提取与四边形透视矫正方案分析

日期：2026-08-19
代码基线：`5a289f7`（v1.5.30）
范围：只分析当前实现、用户提供的两张截图与仓库内同场景验证素材；本报告不修改业务代码。

## 1. 结论摘要

当前实现并非完全没有四点透视能力：`OpenCVLabelRectifier` 已调用
`getPerspectiveTransform + warpPerspective`，`approxPolyDP` 也能产生真正的四边形。
但实际效果仍像“直角矩形矫正”，主要原因有四个：

1. **候选选择以“第一个合法”为准，而不是以“最像标签”为准。** Otsu 亮区排在严格白卡
   之前，只要塑料袋、桌面高光或引导框内的大亮区形成一个凸四边形，就会提前胜出，后面的
   真标签候选不再参与比较。
2. **关键兜底角点来自 `minAreaRect`。** 这四个点永远构成旋转矩形，只能消除平面旋转，
   不能表达近大远小的梯形透视；随后即使调用 `warpPerspective`，输入几何仍是“矩形假设”。
3. **错误矫正也被当作成功。** 现有校验只检查面积、凸性、边长和越界，没有检查四条标签边的
   边缘支撑、标签纸内外对比、文本/码区承载量以及矫正后的水平度，因此“塑料袋四边形”能够
   合法通过。
4. **界面预览不等于模型真实输入。** UI 显示“GLM 输入：码区遮盖未启用”时，
   `VlmOcrEngine` 仍会无条件执行 `VlmInputCropper.cropToTextRegion()`、放大和方形补边。
   用户看到的图与 GLM 实际收到的图不同，且错误透视之后的二次轴对齐裁剪会进一步切掉文字。

因此，新方案不应继续叠加阈值或扩大 `minAreaRect` 的使用范围，而应改成：

> 同时生成所有候选四边形 → 按标签证据统一评分 → 在全分辨率拟合四条独立边线并求交点
> → 置信度合格才做一次透视变换 → 低置信度时保留原 ROI，不做破坏性裁剪。

其中“源区域”必须是四个独立角点组成的任意凸四边形；矫正后的目标图仍应是矩形，这是透视
展开给 OCR 使用的正常目标，不等于用旋转矩形代替源标签边界。

## 2. 样例现象与近似复现

### 2.1 截图观察

- 原始预览中，白色标签四角基本可见，标签本身是明显梯形；引导框内还存在透明袋、白色纸袋、
  木纹桌面、线缆和显示器边框等强干扰。
- 处理结果仍保留大量标签外背景，标签上边没有拉平，右边和下边贴近输出边界并发生截断。
- 这不是简单的“安全边距太小”：输出几何更接近把透明袋或大亮区拉成矩形，而非把白色标签
  四条边拉成矩形。
- 处理结果经过了额外插值和裁剪，但没有换来文字水平与完整边界，因而确实可能比原始 ROI
  更难识别。

### 2.2 对截图内引导框的近似离线复现

说明：以下数据从用户截图的引导框内沿近似裁出，包含截图缩放影响，不替代原始相机帧的精确
标注，但足以复现当前候选优先级问题。

| 通道 | 最大候选面积占 ROI | 结果 | 近似含义 |
|---|---:|---|---|
| Otsu 亮区 | 68.5% | 通过当前四边形校验 | 塑料袋、背景亮区与标签形成的大复合轮廓 |
| 严格白卡 `V>=200, S<=80` | 30.9% | 同样能得到凸四边形 | 与肉眼看到的白色标签边界更接近 |

当前代码先尝试 Otsu 亮区并在成功后立即返回，所以 30.9% 的标签候选没有机会与 68.5% 的
错误候选比较。这个现象与截图中的“外部背景被保留、标签仍斜且被切”一致。

## 3. 当前处理链路

```text
TextureView 抓帧（最大宽 1280）
  -> 按矩形引导框裁 ROI
  -> Java 320px 分析：灰度 Otsu + 纸张 mask + 最大连通区
  -> Java 连通区占比达到阈值（默认 20%）才允许 OpenCV 矫正
  -> OpenCV 640px 分析：
       Otsu 亮 -> Otsu 反相 -> 严格白卡 -> 宽松白卡 -> Canny -> 自适应阈值
       每个通道按面积降序，首个合法 approxPolyDP 四边形立即胜出
       全部失败后使用 minAreaRect；严格白卡内部也会提前使用 minAreaRect
  -> 全分辨率 warpPerspective
  -> 若 OpenCV 失败：Java 逐行 mask/轴对齐裁剪，部分路径再做 Matrix 旋转
  -> 同一处理图送 PP-OCR
  -> UI 展示遮盖后的 structuredInput，称为“GLM 输入”
  -> VLM 内部再次按 QR/条码位置裁半列或横带
  -> 最长边不足 1000 时最多放大 2 倍
  -> 白底补成方图，送入 616x616 视觉模型
```

- `ui/recognition/LabelRecognitionController.java:156-305`

## 4. 根因分析

### P0：通道短路让错误大轮廓抢占真标签

`OpenCVLabelRectifier.rectifyInternal()` 按固定顺序调用检测通道；只要前一通道返回非空，后续
通道就不再执行。`findQuad()` 又按轮廓面积降序，返回第一个通过基础几何校验的四边形。

这实际上把两条不可靠假设写进了决策：

- Otsu 比白卡颜色、边线和内容证据更可靠；
- 面积大的合法四边形比面积小的合法四边形更可能是标签。

在透明袋场景中，两条假设都不成立。透明袋高光、白纸袋和桌面可形成比标签更大的连通轮廓。

### P0：`minAreaRect` 不能完成用户要求的四边形矫正

`detectWhiteCardStrict()` 在 `approxPolyDP` 失败后直接调用 `minAreaRectQuad()`；最终总兜底也
使用同一逻辑。`minAreaRect` 的四点只是旋转矩形的四角，无法表示：

- 上边与下边不平行；
- 左右两边向远端汇聚；
- 四条边因拍摄视角具有不同长度与方向。

它适合作为“仅旋转纠偏”的低置信度降级项，不应标记成“四边形透视成功”，也不应在强制裁边
后直接送 OCR。

### P0：成功校验没有验证“这是不是标签”

`isUsableQuad()` 当前只验证：坐标有限且没有严重越界、边长足够、四边形凸、面积占比在
10%~99%。因此，显示器边框、透明袋、桌面亮区和整个引导框都可能通过。

缺少的关键证据包括：

- 四条候选边上是否确实有连续边缘；
- 四边形内部是否比外侧环带更接近低饱和纸面；
- 内部是否包含多行文本、QR/条码或稳定的高频前景；
- 候选中心、尺度与引导框先验是否合理；
- 试矫正后文字/长边是否更水平，边界是否更完整；
- 第一名与第二名的得分差是否足以支持破坏性裁剪。

### P1：检测门控与真正的 OpenCV 候选不是同一套结果

OpenCV 是否运行，先由 Java 纸张/亮区连通结果与默认 20% 覆盖率决定；OpenCV 内部再用另一套
阈值、分辨率和形态学处理重新找候选。两套检测结果没有共享角点和置信度：

- Java 误判可能阻止本来正确的 OpenCV 四边形参与；
- UI 日志中的“贴纸占比、倾角”来自 Java `LabelRegion`，不代表最终 OpenCV 胜出候选；
- 任意非空 OpenCV 输出都会把 `cropped/deskewed` 设为 `true`，错误矫正也显示为“已旋正”。

建议让 OpenCV 检测结果自身承担置信度判断；Java 结果只能作为一个候选或先验，不能作为硬门。

### P1：Java 回退会保留梯形，却可能跳过旋转

`maskAndCropPaperRegion()` 逐行涂白标签外像素，再按轴对齐外框裁图，并没有进行透视变换。
当 `paperReliable && cropped` 时，后续 Matrix 旋转还会被跳过。此路径能清背景，但会把梯形、
斜边和不均匀缩放原样保留，UI 却只有笼统的“清除标签外区域”状态。

### P1：GLM 输入语义和实际执行不一致

模型配置中的“码区遮盖”只控制 `BarcodeMasker`，但 `VlmInputCropper` 在
`VlmOcrEngine.recognize()` 内始终执行。于是：

- UI 提示“码区遮盖未启用/保留二维码”时，实际仍会裁掉二维码所在半列或条码所在横带；
- UI 的阶段 4 预览不是最终保存到 `vlm_input.png` 的图；
- 无法对“完整标签、遮盖码区、裁文字区”做可信 A/B 对照；
- 如果标签尚未真正拉正，基于轴对齐包围盒和左右半区假设的裁剪容易保留背景、截断文字；
- 直接裁整列还可能丢失右上角 `QTY`、品类等有效文本。

仓库内本场景的历史 `resistor3-vlm-input.png` 也能看到：模型实际输入只保留了左侧文字列的一部分，
但仍夹带较多标签外背景，说明“错误矫正 + 半列裁剪”会相互放大问题。

### P2：重复插值可能损伤小字

当前图像可能依次经历全分辨率透视插值、`VlmInputCropper` 双线性放大到最长边 1000、方形补边
以及模型侧缩放到 616。报告 `ocr_optimize_0819.md` 已记录“矫正后强制 2x 放大无额外收益”，
现实现仍无条件对较小裁图放大。先放大再缩小不会创造笔画信息，反而可能使细小字符边缘变软。

### P2：测试覆盖了几何函数，没有覆盖真实图片决策

现有 `OpenCVLabelRectifierTest` 只在 JVM 中验证角点排序、凸性、越界和面积；没有用 OpenCV native
跑真实标签 fixture，也没有断言哪个候选通道应胜出。`VlmInputCropper` 当前没有对应测试。
因此，“函数能接受一个好四边形”无法阻止“运行时先接受另一个错误四边形”。

## 5. 推荐的新方案

### 5.1 统一结果契约

将 `Bitmap/null` 改成可诊断的结构化结果，例如：

```java
final class LabelRectificationResult {
    Bitmap fullLabel;          // 保留完整标签的标准正视图
    float[] sourceQuad;        // TL, TR, BR, BL，原 ROI 全分辨率坐标
    DetectionMethod method;    // CONTOUR_QUAD / LINE_QUAD / ROTATED_RECT / NONE
    float confidence;          // 0~1
    float runnerUpGap;         // 第一名与第二名分差
    boolean perspectiveFixed;  // 仅真四边形通过时为 true
    String fallbackReason;
    Diagnostics diagnostics;   // 通道、分项得分、输出尺寸、耗时
}
```

`ROTATED_RECT` 必须明确标记为“仅旋转降级”，不能设置 `perspectiveFixed=true`。

### 5.2 所有通道先产出候选，再统一评分

取消“第一个有效即返回”。Otsu、严格/宽松白卡、Canny、自适应阈值和 Java 纸面分量都只负责
提供候选。候选经坐标归一、相似四边形 NMS 去重后统一打分。

建议分项如下，权重需用数据集校准而非永久写死：

| 分项 | 目的 |
|---|---|
| 四边边缘支撑率 | 四条边附近的 Canny/梯度像素占比，排除没有真实边界的大亮区 |
| 纸面内外对比 | 四边形内部的亮度/低饱和比例与外侧环带之差，排除透明袋与木纹背景 |
| 内容承载量 | 内部文本状连通块、QR finder、条码梯度等数量与覆盖，确认候选承载标签内容 |
| 几何质量 | 凸性、角度、边长、透视强度、越界、退化程度；只过滤物理不可能形状 |
| 引导框先验 | 中心距离与面积范围作为弱先验，不能简单奖励“面积最大” |
| 试矫正质量 | 低分辨率试 warp 后的横线水平度、文本行方向、边界留白与背景泄漏 |

必须设置两道门：第一名总分达到阈值，并且第一名相对第二名有足够分差。否则不做破坏性裁剪。

### 5.3 用四条独立边线精修角点

轮廓逼近适合给出初始四边形，但反光、圆角和文字孔洞会让角点漂移。推荐在初始候选附近：

1. 在全分辨率灰度/梯度图上，为每条初始边建立窄带；
2. 收集与该边方向一致的强边缘点，使用 `fitLine` 或带 RANSAC 的直线拟合；
3. 得到上、右、下、左四条独立直线；
4. 相邻直线求交形成真正的 TL/TR/BR/BL；
5. 检查四点唯一、顺时针、凸性与合理透视强度；
6. 沿四条边向外扩 2%~3% 安全边距，再一次性做全分辨率 warp。

这能处理“标签轮廓接近梯形，但 `approxPolyDP` 因圆角/反光没有恰好得到四点”的情况，且不会
退化成 `minAreaRect`。对于边界断裂严重的场景，可增加 Canny + Hough/线段聚类：将线段聚成
两组主方向，从每组选择两条外边线并求交，作为独立的 `LINE_QUAD` 候选。

角点排序也建议从当前 sum/diff 启发式改为“绕质心按极角排序 + 固定顺时针 + 选最左上起点”，
并显式验证四个索引唯一，以覆盖强透视和接近菱形的情况。

### 5.4 低置信度时优先无损回退

推荐的降级顺序：

1. 高置信度真四边形：透视展开并裁切；
2. 只有可靠主方向、没有可靠四边：仅旋转整张 ROI，保留充足边距；
3. 只有纸张分量：可涂白明显背景，但不紧贴分量裁边；
4. 候选冲突或置信度低：保留引导框 ROI，提示调整角度/距离后重拍。

原则是：**不确定时保留像素，比错误裁掉文字更安全。** `minAreaRect` 只能进入第 2 档，不能冒充
第 1 档。

### 5.5 让 PP-OCR 与 GLM 使用同一个“完整标签主图”

透视后的 `fullLabel` 应成为唯一主图，PP-OCR、日志预览和后续派生图都基于它，避免每个模块
再次猜标签边界。

GLM 的码区优化建议改为显式模式：

- `FULL_LABEL`：完整正视标签；
- `MASK_CODES`：只对白色填充精确码区多边形，不裁整列；
- `TEXT_ROI`：利用已经完成的 PP-OCR 文本框并集加安全边距生成文本图，无码框时回退完整图。

不建议继续仅凭“QR 位于左/右半边”裁掉整个半列。若短期保留现逻辑，至少要求：四边形矫正
高置信度、码区多边形完整、裁后保留全部高置信度 OCR 文本框，否则自动回退 `FULL_LABEL`。

阶段 4 必须展示真正写入 `vlm_input.png` 的最终图，并同步显示尺寸、模式和裁剪原因；设置关闭
时不得在引擎内部偷偷执行另一套码区裁剪。

### 5.6 减少重复重采样

- 在分析分辨率找候选，在原始 ROI 上只做一次最终 warp；
- 移除“先双线性放大到 1000、再缩到 616”的固定流程；
- 需要统一到模型输入时，把透视、内容 ROI 与 letterbox 的几何关系合并，最多再进行一次高质量
  缩放；小字缩小时可比较 `INTER_AREA`，放大仅在确有收益的基准结果支持时使用 `INTER_CUBIC`；
- 保留完整正视图给 PP-OCR，GLM 派生图不得反向覆盖主图。

### 5.7 可选的第二阶段：轻量四角/分割模型

如果真实数据扩充后，透明袋、强反光、彩色标签和遮挡使传统 CV 的高置信命中率仍达不到目标，
可训练轻量标签分割或四角关键点模型，输出 mask/四角热力图，再沿边线精修。它应作为候选生成器
接入同一评分和回退框架，而不是绕过置信度门控。当前已有 OpenCV、离线要求明确，建议先完成
上述传统 CV 架构修正并建立数据集，再决定是否增加模型与包体。

## 6. 建议实施顺序

### P0：先止损并恢复可观测性

1. 所有通道候选统一收集与评分，禁止首通道短路；至少让严格白卡真标签候选能击败 Otsu 大袋候选。
2. `minAreaRect` 改名并降级为 rotation-only，不再标记透视成功。
3. `ProcessedFrame` 暴露角点、方法、置信度、分差和失败原因；预览可叠加最终四点。
4. 阶段 4 展示真正的最终 GLM 输入；码区优化设置与实际执行保持一致。
5. 低置信度禁止紧裁，回退完整引导框 ROI。

### P1：补齐真正四边形能力

1. 增加全分辨率四边线拟合与交点精修；
2. 增加 Canny/Hough 断边四边形候选；
3. 增加 2%~3% 透视安全边距与单次重采样；
4. 把 GLM 内容优化改为码区多边形遮盖或 OCR 文本框并集，不再盲裁半列。

### P2：用数据闭环调权重

1. 建立带真实四角和字段文本标注的图片集；
2. 保存候选分项得分、胜出通道、角点和最终模型输入；
3. 用失败样本调评分与阈值，不再以单张图片追加固定阈值分支；
4. 评估是否需要轻量分割/关键点模型。

## 7. 测试与验收建议

### 7.1 必备测试集

首轮至少覆盖以下场景，每类应有不同距离、旋转和透视方向：

- 白标签 + 透明袋强反光；
- 标签旁有白纸袋、线缆、显示器边框；
- 正常桌面、暗背景、低照度和局部阴影；
- 标签四角完整、圆角、局部遮挡、贴近引导框边缘；
- 二维码在左/右、条码在上/下、无任何码区；
- 彩色标签、低对比标签、多个白色矩形同时出现；
- 用户本次电阻标签场景作为固定 golden fixture。

每张图片至少标注：标签 TL/TR/BR/BL、重要文本框、期望字段文本、是否允许仅旋转降级。

### 7.2 建议指标

| 指标 | 首轮验收目标 |
|---|---|
| 平均角点误差 | 不高于图像对角线的 2%，P95 不高于 4% |
| 重要文本保留率 | 100%，任何高置信度文字框不得被裁断 |
| 高置信度误裁率 | 0；不确定样本必须进入无损回退 |
| 矫正后长边残余倾角 | 绝对值不高于 1.5° |
| OCR 退化约束 | PP-OCR/GLM 字段准确率不得低于原始引导框基线，目标应有稳定提升 |
| 可观测一致性 | UI 最终输入预览与实际保存的模型输入像素一致 |
| 性能 | SM-X800 上图像定位与透视 P95 建议控制在 250ms 内，不含 OCR/VLM |

本次 golden fixture 还应添加一条明确断言：Otsu 外部复合轮廓不得胜出；严格白卡/边线形成的
标签四边形应获胜，四条标签边和 2%~3% 安全边距全部保留。

### 7.3 自动化层次

1. **纯几何单测**：强透视、菱形、近退化、角点乱序、重复索引、边线求交与外扩；
2. **OpenCV 图片回归**：真实 PNG 输入，断言方法、角点误差、置信度与输出尺寸；
3. **VLM 派生图测试**：码区在各位置、无码区、文本跨列，断言所有文本框仍在裁图内；
4. **Android 仪器测试**：界面预览与实际 `vlm_input.png` 哈希/像素一致；
5. **端到端字段回归**：同一原图比较原始 ROI、旧实现和新实现的 PP-OCR/GLM 结果。

## 8. 不建议继续采用的优化方式

- 继续把某个固定 HSV/Otsu 阈值提前，而不改变全候选评分；换场景后仍会被新的大亮区抢占。
- 扩大 `minAreaRect` 使用范围并称为四边形矫正；它无法表达透视梯形。
- 只看“最终某次字段识别正确”就认定裁剪正确；融合或解析器可能偶然补回错误，不能证明图像前置可靠。
- 在错误裁剪后继续放大、锐化或二值化；丢失的边界和文字无法由增强恢复。
- 让 UI 展示中间图，却把另一个未展示的派生图送入模型。

## 9. 最终建议

优先实施 P0。它不要求新增模型，主要是重构当前 OpenCV 候选决策、降低 `minAreaRect` 权限并
打通真实输入预览，能够直接解决本次样例中“塑料袋大轮廓抢占标签”和“界面所见非模型所得”
两个核心问题。随后用边线拟合把真正四边形能力补完整，再基于带四角标注的数据集调评分。

衡量成功的标准不应是“调用过 `warpPerspective`”，而应是：选中的四个源角点确实属于标签，
所有重要文字都被完整保留，矫正后的图比原始 ROI 更利于 PP-OCR 与 GLM；做不到时必须安全回退。

## 12. v1.5.33 反光抑制与单位排版（2026-08-20）

### 12.1 反光优化流程

反光处理接在真四边形拉正/安全回退之后、PP-OCR 与 GLM 分流之前，两路模型因此使用同一张图：

1. 在标签亮纸区域估计大尺度光照场，统计光照变异系数和接近过曝的像素比例；
2. 只有光照不均达到阈值时才启动除法光照归一化，避免均匀图片被无谓重处理；
3. 使用低强度 CLAHE 恢复浅色小字对比，再以轻量反锐化补偿处理造成的边缘软化；
4. 重新估计大尺度光照变化，至少改善 3% 才采纳，否则继续使用原图；
5. UI 日志明确显示“已应用”及处理前后光照差异，或说明未达到阈值/收益不足。

该流程不对完全过曝区域执行内容修补：单帧已经丢失的笔画无法可靠重建，伪造式 inpaint 可能引入
错误字符。强反光仍应优先通过改变灯光/相机角度或多帧采集解决。
