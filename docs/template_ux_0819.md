# 便签模板排版与交互优化日志

日期：2026-08-19
目标（用户要求）：
1. 排版自动适配各种便签大小，并根据便签大小取舍字段。
2. 加分隔线等元素，让便签更规整。
3. 预览默认不选中任何元素（选择框点按后才显示）。
4. 选择框刚好包住文本，而不是默认大小（元素 heightMm 默认 8mm 导致）。

## 现状问题（代码勘察结论）

- `ComponentLabelFactory.create` 先按 25×15 生成再整体缩放：只缩字号/坐标，不做字段取舍，
  小标签挤爆、大标签空旷。
- 文本元素 `heightMm` 用构造器默认 8mm → 选择框/裁切盒与文字脱节。
- `LabelCanvasView.setDocument` 与 5 处调用方默认选中首元素 → 橙色框常驻。
- 字宽估算 0.55em/半角偏乐观 → 长型号在预览中折行溢出（真机截图证实）。
- 分隔线元素类型（TYPE_LINE h/v）预览/缩略图/打印三链路早已支持，模板未使用。

## 改动清单（v1.5.29 候选）

- `ComponentLabelFactory` 重写为按目标尺寸直接排版：
  - 行距 = 可用高度 / 行数；字号 = 行距 × 0.72 填充系数（largeFont ×1.1）。
  - 行距 < 2.0mm 时按优先级丢字段：参数(10) → 品牌(40) → 品类(60) → 立创(70) → 封装(80) → 规格(90)，
    型号(100) 最后保留。
  - 前缀列宽按"参数："实测 + 0.15mm 呼吸位自适应，上限 5.0mm（防长型号被挤进截断）。
  - 边距 0.3mm、列间隙 0.15mm；字宽估算半角 0.6em、粗体 1.05、fit 留 1% 呼吸位。
  - 元素 heightMm = 行距 × 0.95（真实行高，供预览裁切与选择框贴字）。
- 分隔线（`addSeparators`）：前缀/值列竖线 + 首行下横线常驻；行距 ≥2.8mm 再补全行间横线
  （大标签表格化）。线宽 0.15mm。
- `LabelCanvasView`：
  - `setDocument` 不再回退选中首元素；MainActivity(2 处)/ComponentTemplateController/
    EmbeddedScannerController/ElementEditorController 的 `select(first.id)` 全部移除。
  - `calculateElementBounds` 对文本元素用 StaticLayout 实测宽高（右对齐贴右缘、居中贴中线），
    选择框刚好包字。
- 测试：`ComponentLabelFactoryTest` 更新 + 新增 3 例（分隔线存在性、20×10 取舍、40×30 全字段+行间线）。

## 结论

四项需求全部落地并真机验证：任意尺寸自适应排版（行距驱动字号 + 优先级取舍）、
分隔线（竖线常驻，行距 ≥2.8mm 时表格化）、默认无选中、选择框贴字。
预览/缩略图/打印三路共用 LabelDocument 元素流，效果自动一致。

## 第二轮（2026-08-19 晚，用户反馈四点）

1. **分隔线做成可选项**：模板配置新增"分隔线"复选框（`templateSeparatorCheck`，
   `ComponentTemplateStore` 持久化 key `separators`，默认开）；工厂 `create()` 新增
   `separators` 参数，缩略图/重排/换尺寸全链路传递。
2. **型号跟随字数自动缩小到单行**：新增 `render/TextFitUtil.fitSingleLine()`——
   渲染层用 `Paint.measureText` 实测收缩字号（预览 `LabelCanvasView` + 打印
   `LabelBitmapRenderer` 共用，估算偏乐观由渲染层收口）；工厂截断前增加 4.0pt 硬下限
   （`FIT_HARD_MIN_PT`，`LabelDocument.normalize` 字号下限同步 4.5→4.0），尽量避免丢字符。
3. **值列贴线问题**：列间隙 0.15→0.4mm，竖线居中后前缀/值文字各留 0.2mm 呼吸位。
4. **333.333mW→3.33mW 疑点**：怀疑采样惩罚（presence/frequency 惩罚重复字符 '3'）
   或分辨率；合成图对照实验进行中（penalty 1.3/0.3/0.2 vs 1.0/0/0）。
   注：S1 已证实重惩罚会腐蚀重复字符（CGA04O2COG…），轻惩罚对 6 连 '3' 的影响待实测。

### 333.333mW 诊断（合成图对照，616 转写）

| 采样 | "333.333mW 1%" 行 | 其他行 |
|------|-------------------|--------|
| penalty 1.3/0.3/0.2 | **完全正确** | 内部码掉字（30-R-RO6-003）、MPN 一处 0→O |
| penalty 1.0/0/0 | **完全正确** | MPN 正确，内部码略误（300-R06-003） |

结论：**轻惩罚不会吞重复 '3'，模型在 616 下读 333.333mW 无问题** → 误读另有其因，
最大嫌疑是 **PP-OCR 把小字读成 3.33mW 后，融合 2 档让 PP 赢冲突**（用户扫描时生效的
正是 2 档）。待用户把电阻标签放回摄像头前做双通道实锤（截图日志窗格可同时看到
PP 原文与 VLM 转写）。

## 第三轮（2026-08-19 深夜）：333.333mW 全链路修复 + 实时性修复

### 333.333mW 根因链（三层，逐层实锤）

1. **矫正未触发**：电阻标签在透明袋中倾斜 ~10°，宽松白卡阈值（V≥140）把袋高光与
   标签连通 → Otsu/白卡/Canny 全通道失败 → 倾斜大场景原图直接进 VLM。
2. **视觉 token 预算被码区吃掉**：即使矫正成功（465×421），616² 方形预算下小字号
   规格行仅 ~15px → VLM 把 "厚膜电阻 0Ω 333.333mW" 读成 "3mW"/"3mV"（840 也一样）。
   **文字列裁剪（去 QR 列 + 去底部条码带）后同模型同参数读得 "厚膜电阻 0Ω 333.333mW" 全对**；
   含条码带的全高左列则退化为 "3.33mW"（条码带干扰阅读顺序）。
3. **解析器混合行缺陷**：混合行 "厚膜电阻 0Ω 333.333mW" 旧逻辑整行归品类、规格丢弃；
   残读垃圾行 "3.00mW" 还会先抢占规格。

### 修复内容

- `OpenCVLabelRectifier` 新增严格白卡通道（V≥200、S<80，袋/桌面剥离），
  approxPolyDP 不出四边形时采纳最大分量 minAreaRect（重构出 `minAreaRectQuad` 共用）。
- 新增 `scan/vlm/VlmInputCropper`：ZXing 检出 QR → 裁掉码所在半列；一维码 → 裁掉所在
  横带；裁后适度放大（≤2x，最长边补到 1000px）。接入 `VlmOcrEngine.recognize` 前置。
- `LabelTextParser`：混合行拆分（中文段→品类、单位段→规格候选）；
  规格候选改"单位值多者胜"（0Ω 333.333mW 压过 3.00mW 残读）。
- `ComponentRecordStore`（新）：识别结果持久化；`MainActivity` 启动恢复 + 有记录时
  按当前模板配置重排一次。修复用户反馈的"分隔线切换/尺寸切换不实时生效"
  （重启后 record 为 null 导致 regenerate 提前返回）。
